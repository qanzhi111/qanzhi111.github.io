三、技术细节深度分析

3.1 攻击架构

Lazy Summer Protocol 采用 Fleet Commander + Strategy (Ark) 的分层架构：


用户存款 → Fleet Commander → Strategy Contracts (Ark/Silo Finance) → SiloVault
                 ↑
            计算 totalAssets() 依赖各 Strategy 报告的余额

核心信任假设：Fleet Commander 信任每个 Strategy（Ark）报告的内部余额数据来计算 totalAssets()，而非独立验证实际资产状态。

3.2 攻击步骤拆解

Step 1：闪电贷获取巨量资金


攻击者 → Aave/Balancer 闪电贷 → 借入 65,400,000 USDC + 1,000,000 USDT

Step 2：正常存款获取份额


65,400,000 USDC → Fleet Commander deposit → 获得相应 Fleet 份额

此步骤完全正常，目的是获取合法的 Fleet 存取权限。

Step 3：绕过存款流程的"份额转移"（攻击核心）


攻击者直接将 SiloVault 份额（原本应通过正常 deposit 流程获得）
→ 转入由 Silo Finance 管理的策略合约 Ark

关键操作：攻击者绕过了 SiloVault 的正常存款流程，直接将份额"塞入" Ark 合约。这使得 Ark 报告的余额从 0 膨胀至 7,140,000 美元。

Step 4：利用信任机制获利


Fleet Commander 读取 Ark 报告的 inflated balance → 
计算 totalAssets() = 正常余额 + 7,140,000（虚增部分）→
攻击者赎回 71,000,000 USDC → 净获利 ~6,100,000 USDC

Step 5：偿还闪电贷 + 退出


偿还闪电贷本金 + 手续费 → 剩余利润转至攻击者地址

3.3 根本原因：ERC-4626 信任边界缺陷

ERC-4626 代币化金库标准定义了统一的存款/提款/份额计算接口，但未规范跨金库信任验证机制：


// Fleet Commander 的 totalAssets() 实现
function totalAssets() public view returns (uint256) {
    uint256 total = 0;
    for (uint i = 0; i < strategies.length; i++) {
        total += strategies[i].totalAssets();  // ← 盲信每个 Strategy 的报告
    }
    return total;
}

问题：当攻击者可以直接向 Strategy 合约转入份额（不经过正常 deposit 流程）时，Strategy 报告的 totalAssets() 会膨胀，但 Fleet Commander 无法区分"真实收益"和"外部注入份额"。

这是 ERC-4626 标准的"捐赠攻击"变体 — 类似于 ERC-4626 早期已知的 inflation attack，但扩展到了跨合约层级。

五、防御建议

5.1 协议层面

  1. 内部余额验证：Fleet Commander 应独立验证 Strategy 的实际资产状态，而非仅读取 totalAssets() 报告
  2. 份额来源追踪：记录份额的 deposit 路径，区分"正常存款产生的份额"和"外部转入的份额"
  3. 存款流程强制：禁止绕过 deposit 流程直接持有 Vault 份额
  4. 份额变更审计：监控 Strategy 余额的异常膨胀事件

5.2 标准层面

  1. ERC-4626 补充规范：建议在 EIP 层面增加"份额来源验证"的最佳实践
  2. 跨金库通信协议：建立金库间的安全余额查询标准

5.3 用户层面

  1. 分散存款：避免在单一聚合协议存入过多资金
