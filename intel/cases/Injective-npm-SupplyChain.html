Injective npm 供应链攻击调查报告

> 调查日期：2026-07-10

> 事件时间：2026-07-08 (恶意版本发布 ~49分钟内被发现)

> 调查状态：进行中

> 来源：Socket Research、StepSecurity、Cointelegraph、OX Security、BleepingComputer

事件概述

2026年7月8日，攻击者通过入侵Injective Labs维护者的GitHub账号，向官方TypeScript SDK @injectivelabs/sdk-ts 注入恶意代码后门。该后门劫持钱包密钥派生函数，窃取私钥和助记词，并伪装成正常遥测数据外传至攻击者控制的基础设施。

恶意版本 v1.20.21 被同步发布至18个关联npm包，暴露窗口约49分钟。恶意代码被下载约310次，但其传递影响范围可能更广——87个下游依赖包、合计112,378次下载。

损失金额：未知（尚未确认是否有钱包资金被盗）

影响范围：Injective区块链生态所有使用官方SDK的应用开发者

技术攻击分析

攻击链（5阶段）

Stage 1: 维护者账号入侵

  • 攻击者获取了Injective Labs某维护者的GitHub账号访问权
  • 直接向master分支推送恶意代码
  • npm provenance attestation验证显示发布来源为被入侵的维护者账号

Stage 2: 恶意载荷注入

  • 恶意文件：key-derivation-telemetry.ts
  • 伪装为合法的遥测/分析功能
  • 劫持 PrivateKey.fromMnemonic() 和 PrivateKey.fromHex() 函数
  • 这两个函数是SDK中将助记词/私钥转换为可用签名密钥的标准入口点

Stage 3: 触发机制

  • 每当应用调用钱包创建/加载函数时，恶意代码自动执行
  • 在密钥生成/恢复的瞬间截取最敏感数据
  • 无需破解加密或攻击协议层——直接读取明文密钥

Stage 4: 批量编码与外传

  • 窃取数据经过编码后发送至：testnet.archival.chain.grpc-web.injective.network
  • 伪装成正常Injective gRPC流量
  • 设计目的是绕过基于域名信誉的网络监控

Stage 5: 传播放大

  • 恶意版本被pin至18个 @injectivelabs 作用域下的包
  • 任何安装这17个关联包之一的开发者都会自动安装被入侵的SDK
  • 开发者可能根本不知道自己安装了恶意依赖

独特分析角度

1. "49分钟窗口"——供应链攻击的速度竞赛

从恶意发布到被废弃仅49分钟。但310次下载 + 87个下游包 + 112K总下载 = 爆炸半径远超表面数字。这49分钟对于CI/CD流水线自动拉取的开发者来说，足以造成不可逆的密钥泄露。速度已成为供应链攻击的核心武器——检测窗口在分钟级别，而密钥泄露的后果是永久的。

2. 2026年Web3供应链攻击进入"SDK级"阶段

对比今年已记录的供应链攻击：

  • npm Web3 SupplyChain（6月）：针对npm上伪造Web3包
  • GitHub/NPM Supply Chain（5月）：针对开发者仓库
  • TrapDoor（5月）：针对加密/DeFi/AI/安全开发者
  • Injective（7月）：直接攻击官方SDK的密钥派生函数

攻击目标从"开发者工具"升级到"开发者工具的核心函数"。这不是向npm上传假包——这是入侵官方维护者账号，在真实代码仓库的真实密钥处理路径上植入后门。

3. "伪装成遥测"——AI时代的社会工程进化

恶意代码伪装成"key-derivation-telemetry"（密钥派生遥测），C2端点伪装成testnet.archival.chain.grpc-web.injective.network——一个看起来完全合法的Injective测试网gRPC地址。

这种伪装策略说明攻击者：

  • 深度理解Injective的网络架构
  • 知道开发者不会审查"遥测"类流量
  • 选择了域名信誉检查最可能放行的端点命名

4. 与ChainSentinel的关联

Injective攻击直接验证了ChainSentinel"AI Agent链上独立审计"的核心需求：

  • SDK供应链审计：持续监控官方SDK依赖变更
  • 密钥派生路径监控：检测SDK中敏感函数被修改
  • 维护者账号安全：检测异常commit模式和权限变更

5. CertiK数据佐证

CertiK Q2 2026报告：钱包泄露是最昂贵的攻击类型，H1 2026损失$4.44亿/33起事件。Injective攻击如果成功窃取开发者密钥，可能导致远超SDK本身的连锁损失——一个开发者的密钥泄露可能影响其构建的所有应用的用户。

应急响应建议

开发者立即行动

  1. 检查 package-lock.json / yarn.lock，确认是否存在 @injectivelabs/sdk-ts@1.20.21
  2. 如在暴露窗口内运行过密钥派生逻辑，立即轮换所有私钥和助记词
  3. 升级至 @injectivelabs/sdk-ts@1.20.23 或更高版本
  4. 审查CI/CD管道中的npm install日志
  5. 为npm账号启用2FA，锁定精确依赖版本

行业层面

  1. SDK维护者应启用硬件2FA + commit签名验证
  2. npm包应实现自动化安全扫描（Socket、Snyk等）
  3. 关键密钥派生函数应独立审计，不应被"遥测"功能劫持
